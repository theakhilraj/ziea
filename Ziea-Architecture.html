1 System Overview

ZIEA is a premium women's-wear storefront for the Kerala market, built as a single Next.js 16 App-Router application with a Supabase backend. One codebase serves two audiences: a public storefront (mostly statically rendered for speed) and a private admin console (fully dynamic, role-gated).

Framework
Next.js 16 (App Router, Turbopack), React 19 Server Components
Backend
Supabase — Postgres, Auth (JWT), Realtime, Row-Level Security
Styling
Tailwind v4 @theme tokens · next/font (Playfair + Jost)
Media / CDN
Hostinger filesystem CDN (public_html/cdn) served via a Node route
Ordering
WhatsApp click-to-chat (wa.me) — order logged in DB, no payment gateway
Hosting
Live on ziea.in — Hostinger Node.js Web Apps (Business plan)
⚠️
Not the Next.js you know. This app runs Next.js 16, whose middleware file is renamed proxy.ts, whose params/searchParams are async Promises, and where next/image's priority prop is deprecated in favour of preload+fetchPriority. All patterns below reflect the v16 conventions.

3 Customer Rendering & Data Flow

The golden rule: reading a cookie forces dynamic rendering. Pages that only need catalog data go through a cookie-less cached client and stay static/ISR; pages that need "who is this user" (cart, wishlist) read cookies and render dynamically.

🔑
The static trick for wishlist hearts. A product grid needs to know which items you have hearted — which would normally force a cookie read and make the page dynamic. Instead, ZIEA keeps the wishlist as a client-side WishlistProvider context that fetches your IDs after hydration. The server-rendered grid stays 100% static; the hearts light up a moment later on the client.

Two image JSON shapes coexist. Product/category images store { url, is_highlight, crop_x, crop_y, zoom } (snake_case); branding images store { url, cropX, cropY, zoom } (camelCase). Both encode a focal-point crop so the same asset can be reframed per surface without re-uploading.

Likewise products.status, badges, delivery_days and the category crop columns were added after the SQL files were written. Treat those specific schemas as live-DB-verified, not repo-verified.

5 Data APIs & Server Actions

Mutations split into two styles. Server Actions (app/actions/*.ts) handle cart & wishlist — they run on the server, use the fast local-JWT identity, and defer logging with after(). Direct browser inserts handle public writes (contact, orders, newsletter) guarded by public-INSERT RLS.

Example — the cart upsert (deferred logging)

// app/actions/cart.ts — identity via local JWT, logging deferred past the response
export async function addToCart(productId, size = null, qty = 1) {
  const userId = await getUserId();        // getClaims() — no network hop
  if (!userId) return { error: "unauthenticated" };
  // upsert: bump quantity if (product_id,size) already in cart, else insert…
  after(() => logProductInteraction(productId, "Cart")); // runs after response is sent
  revalidatePath("/cart");
}
🔑
Why getUserId() and not getUser()? getUser() makes a network round-trip to Supabase's Auth server (200–800 ms). getUserId() verifies the session JWT locally via getClaims() — instant. RLS still enforces ownership on every row, so the fast path is safe for cart/wishlist mutations.

6 Caching Architecture

The storefront is fast because catalog reads are memoised with unstable_cache, keyed and tagged, then served from cache until an admin edit fires revalidateTag. All cached readers use a cookie-less createPublicClient() — the one client legal to call inside a cache boundary.

One cache entry serves every filter. getCatalogRows(category, q) is keyed only on category + search text; all other filters, sorting and pagination happen in-memory on the cached rows. So a shopper toggling price/size/colour filters never triggers a fresh DB query.

7 Authentication & Tokens

Auth is Supabase's JWT session model over @supabase/ssr cookies. A short-lived access token (a signed JWT) is verified locally; a long-lived refresh token silently mints new access tokens. The proxy.ts middleware keeps both fresh on every request.

Row-Level Security is the real guard. Because every cart_items/wishlist_items/orders query is filtered by user_id and RLS policies enforce ownership in Postgres, a forged client request can never read or mutate another user's rows — even though identity is resolved from a locally-verified JWT.

8 Storefront Sections

Each customer surface, what it renders and where its data lives.

Collections

CategoryTabs + a portalled FiltersPanel side-sheet + server ProductGrid. Facets and rows come from cached getProductFacets/getFilteredProducts. 32 products per page; the first two cards on page 1 are preloaded as LCP. Route-level loading.tsx shows a rotating LoadingQuote.

Product Detail

Gallery, info, Buy Now + Add to Cart actions, related products, and a ViewTracker that fires incrementProductView. Prerendered per product_code; carries Product JSON-LD.

About Us

Sticky editorial layout — hero, narrative, craftsmanship carousel, philosophy — all imagery driven by the branding_assets "About Us" row so it's editable without a deploy.

Contact Us

A client form (type = business / personal / collaboration) that inserts directly into contact_messages and logs an activity_logs entry. Surfaces in the admin Enquiries inbox in real time.

Customisation Studio

A static, mobile-responsive landing page at /customisation — hero + trust badges, three "experience" cards (Consultation / Inspiration / Customise ZIEA), a 6-step process timeline, an editorial testimonial and a WhatsApp help CTA. Built from server components under components/server/customisation/, reusing Header/Footer/Button. Every journey CTA is wa.me click-to-chat with a contextual pre-filled message; the hero button anchor-scrolls to the experience cards. Hero & testimonial imagery are branded placeholders with one-line swap points.

Wishlist

Dynamic page joining wishlist_items ⋈ products. Optimistic remove / "move to cart"; badge count driven by the ziea:counts-changed window event.

Shopping Cart

Dynamic page joining cart_items ⋈ products. Optimistic quantity stepper; CartCheckoutButton assembles a WhatsApp message and records each line as an order.

🔑
The ziea:counts-changed event bus. Any add/remove dispatches a lightweight window event; the header's cart & wishlist badges and the WishlistProvider all listen and re-fetch. No global state library — just a DOM event keeping every corner of the UI in sync.
💡
Entry point moved. The header nav "Customization Studio" link (desktop & mobile) now routes to the new static /customisation landing page instead of /contact-us?type=personal. The contact form and its personal tab are unchanged and still reachable directly.

9 WhatsApp Order Flow

ZIEA takes orders over WhatsApp click-to-chat — no payment gateway. The order is recorded in the DB first, then the customer is handed off to WhatsApp, so no lead is ever lost even if they abandon the chat.

  1. Buy Now / Checkout. Shopper confirms in a modal (guests give name + phone, Zod-validated; members are auto-filled from their profile). client
  2. Record the order. One orders row per line item is inserted with status:"Initiated" and source:"buy_now" or "cart", plus an activity_logs entry. orders
  3. Hand off. window.open(orderHref(items)) fires synchronously inside the click so the pop-up isn't blocked — opening wa.me/918139045083 with a pre-filled message. wa.me
  4. Admin fulfils. The order appears in /admin/orders as "New"; the admin advances it Initiated → Confirmed → Fulfilled (or Cancelled). admin
// utils/whatsapp.ts — the pre-filled message body
Hi ZIEA, I'd like to place an order:

• Kerala Cotton Kurthi (Code: Z-0042) - Size M, Qty 1 - ₹1,499
// Subtotal line appended only when more than one item
Please confirm availability & payment. Thank you!
✅
Guest-friendly & loss-proof. Buy-Now works without an account, and because the write precedes the redirect, every intent to buy lands in the orders table for the admin to follow up — turning a casual WhatsApp tap into a tracked lead.

12 Activity Tracking

The admin sees a running feed of customer behaviour via activity_logs. Interaction logging is best-effort and deferred — it never slows a customer action, and it's skipped entirely for admin accounts so the admin's own clicks don't pollute the feed.

Activity typeFired byPath
Customer Login / Admin LoginAuth callbackapp/auth/callback/route.ts
Customer RegistrationDB trigger on new userlog_user_registration_activity
Cart / WishlistlogProductInteraction via after()actions/cart.ts, wishlist.ts
Newsletter SubscriptionsubscribeNewsletteractions/newsletter.ts
Category / Product Added·Updated·DeletedAdmin CRUDadmin clients
Enquiry & Order eventsContact form / order flowclient inserts
💡
Views are counted, not logged. Product views bump a products.view_count counter through an RPC — they are not written to activity_logs. So the analytics "views" number comes from the counter, while the activity feed shows discrete events (logins, cart/wishlist adds, sign-ups, enquiries, orders).
🔑
What the admin can observe about a customer: when they logged in, when they registered, every add-to-cart and add-to-wishlist (with product name + code), newsletter sign-ups, submitted enquiries, and placed orders — surfaced both in the Activity feed and live via the notification bell. Casual page views are aggregated as counts only, never tied to an individual in the feed.

13 SEO Architecture

SEO is code-generated from a single source of truth (utils/site.ts): robots, sitemap, PWA manifest, per-page canonicals, Open Graph/Twitter cards, and JSON-LD structured data — which is why SEO scores 100 on both form factors.

FileEmits

app/sitemap.tsStatic routes + every published product (/collections/{code}) + category URLs, via cached getAllPublishedSlugs
app/manifest.tsPWA manifest — name, icons, theme_color #2C3829, background_color #F5F0E8
app/layout.tsxmetadataBase, title template %s | ZIEA, default OG/Twitter, Organization JSON-LD
app/collections/[slug]Per-product OG, self-canonical, and Product JSON-LD (price, currency INR, in/out-of-stock)
⚠️
One canonical rule that bit us. A global alternates.canonical in the root layout would make every page canonicalise to / (collections once wrongly pointed home). The fix — and current design — is no global canonical; each public page declares its own self-referential canonical.
🔑
Origin is env-driven. SITE_URL comes from NEXT_PUBLIC_SITE_URL, now set to https://ziea.in in the Hostinger app env — so canonicals, OG tags and the sitemap all resolve to the production domain. (The code default remains https://ziea.vercel.app only as a fallback if the env var is ever missing.)
